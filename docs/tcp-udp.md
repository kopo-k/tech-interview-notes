# TCP / UDP の違い

## 1分サマリ

TCP は「**確実に・順番通り・全部届ける**」ことを OS が面倒見てくれるコネクション型プロトコル。UDP は「**投げっぱなし**」の軽量プロトコル。

- 信頼性が必要 → TCP（HTTP/1,2、SSH、SMTP）
- リアルタイム性が必要、多少のロスは許せる → UDP（DNS、動画ストリーミング、VoIP、ゲーム）

面接で 15 秒で答えるなら：「**TCP はコネクション型で信頼性・順序保証あり、UDP はコネクションレスで投げっぱなし、その代わり速くてオーバーヘッドが小さい**」。

---

## 本質の理解

### なぜ「2つ」あるのか

IP（Internet Protocol）はそもそも「**届くかわからない**」プロトコル。パケットは消えるし順序も入れ替わる。

- 毎回アプリ側で「再送ロジック」「並べ替えロジック」を書くのはダルい → OS が肩代わりしてくれるのが **TCP**
- でも音声通話やゲームでは「再送してる間に古いデータが来ても無意味」 → 保証を捨てた軽量版が欲しい → **UDP**

つまり「**信頼性をOSがやるか、アプリがやるか、そもそも要らないか**」の選択肢。

### TCP の信頼性は何で実現されている？

1. **シーケンス番号**: 各バイトに番号を振る → 順序を復元できる、欠落も検出できる
2. **ACK（確認応答）**: 受信側が「ここまで受け取った」と返す
3. **再送**: 一定時間 ACK が来なければ送り直す
4. **フロー制御**: 受信側のバッファに余裕がある分だけ送る（ウィンドウサイズ）
5. **輻輳制御**: ネットワークが混んでたら送信量を絞る（スロースタート、輻輳回避）

## 対比表

| 観点 | TCP | UDP |
|---|---|---|
| 接続 | コネクション型（3way ハンドシェイク） | コネクションレス |
| 信頼性 | 再送・順序保証あり | なし（投げっぱなし） |
| ヘッダサイズ | 20 バイト〜 | **8 バイト固定** |
| フロー制御 | あり（ウィンドウ） | なし |
| 輻輳制御 | あり | なし |
| ブロードキャスト/マルチキャスト | × | ○ |
| 速度 | 遅い（オーバーヘッド大） | 速い |
| 代表的なポート | 80(HTTP), 443(HTTPS), 22(SSH) | 53(DNS), 123(NTP) |
| ユースケース | Web、ファイル転送、メール | DNS、動画配信、VoIP、ゲーム、QUIC(HTTP/3) |

### 3way ハンドシェイク（TCP のコネクション確立）

```
クライアント        サーバ
    |  --- SYN --->   |   「接続したい」
    |  <-- SYN/ACK -- |   「OK、こちらも接続したい」
    |  --- ACK --->   |   「了解、確立」
    |                 |
    |   データ送信開始 |
```

なぜ 3 回？ → **双方向**で「相手が受信できる状態」を確認するため。お互いに SYN と ACK を交換する必要があり、サーバ側の SYN と ACK は同じパケットにまとめられるので合計 3 回になる。

## ハンズオン

### 1. TCP サーバ/クライアントを `nc` で立てる

ターミナルを 2 つ開く。

**ターミナル A（サーバ）**:
```bash
nc -l 12345
```

**ターミナル B（クライアント）**:
```bash
nc localhost 12345
```

B で文字を打って Enter → A に届く。**コネクションが張られている**ので、片方を `Ctrl+C` で切ると相手も終わる。

### 2. UDP で同じことをやる

**ターミナル A（サーバ）**:
```bash
nc -u -l 12345
```

**ターミナル B（クライアント）**:
```bash
nc -u localhost 12345
```

文字は届く。ただし試しに**サーバを起動する前に**クライアントから文字を投げてみると：

- TCP: クライアントが「Connection refused」で落ちる
- UDP: クライアントは**何事もなかったかのように動き続ける**（投げっぱなし）

これが「コネクションの有無」の差。

### 3. パケットを観察する（tcpdump）

別ターミナルで（要 sudo）:
```bash
sudo tcpdump -i lo0 -n port 12345
```

その状態で TCP セッションを張ると：

```
IP localhost.xxxxx > localhost.12345: Flags [S], ...     # SYN
IP localhost.12345 > localhost.xxxxx: Flags [S.], ...    # SYN-ACK
IP localhost.xxxxx > localhost.12345: Flags [.], ...     # ACK
```

`Flags [S]`, `[S.]`, `[.]` が 3way ハンドシェイク。UDP では出てこない。

### 4. ヘッダサイズを実感する

```bash
# 任意のサイトに HEAD リクエスト → TCP の挙動
curl -v https://example.com 2>&1 | head -20

# DNS は UDP で 1 往復で終わる
dig example.com
```

DNS が UDP なのは「1 往復で済むのにコネクション張るの無駄」だから。逆に DNS でも応答が大きい（DNSSEC など）と TCP にフォールバックする。

## よくある誤解と落とし穴

### ❌ 「HTTP は TCP の上で動く」だけ覚えている
✅ **HTTP/3 は QUIC（UDP ベース）**。「Web = TCP」は古い知識。QUIC は UDP の上に独自に信頼性・順序保証・暗号化を載せる。「TCP の 3way + TLS の handshake」で接続確立が遅い問題を解決するために UDP に降りた。

### ❌ 「UDP は信頼性ゼロ」
✅ **チェックサム自体はある**（破損は検出される、ただし破棄されるだけ）。「再送・順序保証がない」だけ。

### ❌ 「UDP は速い、だから使う」
✅ 「コネクション確立・状態管理が不要 → オーバーヘッドが小さい → 結果として速い・軽い」が正確。「速いから採用」ではなく「**保証がいらないなら不要な処理を削れる**」。

### ❌ 「3way ハンドシェイクの SYN-ACK は 2 つのパケット」
✅ 1 パケット。SYN と ACK のフラグが両方立っているだけ。

### ❌ 「TCP なら順番が必ず正しい」
✅ ネットワーク上は順序が崩れることがあるが、**受信側の OS がシーケンス番号で並べ直してからアプリに渡す**。アプリ視点では順番通りに見える。

## 章末 Q&A

> 答えを見る前に自分で言ってみてください。

**Q1. TCP の 3way ハンドシェイクで送られるパケットを順に挙げ、それぞれの役割を述べよ。**

<details>
<summary>解答</summary>

1. **SYN** (Client → Server): クライアントが接続要求。初期シーケンス番号を伝える
2. **SYN-ACK** (Server → Client): サーバが「受け取った」と ACK しつつ、自分側のシーケンス番号も送る
3. **ACK** (Client → Server): クライアントがサーバの SYN を ACK する

これで双方向の通信路が確立される。
</details>

**Q2. なぜ DNS は UDP を使うのか？ 例外はあるか？**

<details>
<summary>解答</summary>

- **理由**: ほとんどの DNS クエリは 1 パケットで完結するため、コネクション確立のための 3way ハンドシェイクが純粋なオーバーヘッドになる。UDP なら 1 往復で済む。
- **例外**: 応答サイズが大きい場合（DNSSEC、ゾーン転送 AXFR）は TCP にフォールバックする。DNS 仕様にもこのフォールバックが定義されている。
</details>

**Q3. UDP で信頼性が必要になったらどうするか？**

<details>
<summary>解答</summary>

アプリ層で「シーケンス番号 + ACK + 再送」を自前で実装する。これを標準化して TLS と組み合わせたものが **QUIC**（HTTP/3 のトランスポート）。

「だったら TCP 使えばいい」と思えるが、TCP には「head-of-line blocking（1 パケットの遅延で後続が全部止まる）」などの問題があり、QUIC はそれを解決するために UDP に降りて独自実装している。
</details>

**Q4. 受信バッファが溢れたら TCP はどう振る舞う？**

<details>
<summary>解答</summary>

**フロー制御**が働く。受信側は ACK の中で「あと N バイト受け取れる」というウィンドウサイズを送信側に伝え、送信側はそれを超えて送らない。ウィンドウが 0 になれば送信は止まり、受信側がバッファを空けてウィンドウを広げるのを待つ。
</details>

**Q5. オンラインゲームで「位置同期」を実装するならどっち？**

<details>
<summary>解答</summary>

**UDP**。理由は「**古い位置情報は再送されても無意味**」だから。TCP だと 1 パケット落ちただけで以降のパケットが届かない（HoL blocking）。UDP なら欠落パケットは捨てて最新の位置を即座に処理できる。ただしチャットやアイテム取引のような「絶対に届かないと困る」処理は TCP（または信頼性レイヤを別途）で送る。
</details>
