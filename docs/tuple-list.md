# タプル と リスト の違い（Python）

## 1分サマリ

両方とも順序付きのコレクション。違いはたった一つから派生する：

- **リスト `[]`** = **ミュータブル**（変更可能）
- **タプル `()`** = **イミュータブル**（変更不可）

この「変えられるかどうか」から、次の違いが全部出てくる：

| 派生する違い | 理由 |
|---|---|
| タプルは **dict のキーや set の要素にできる** | 不変だからハッシュ値が変わらない |
| タプルは **メモリ・生成速度で有利** | 拡張用バッファが要らない |
| メソッド数が違う | リストは `append/pop/sort/...`、タプルは `count/index` のみ |
| **設計の意図が違う** | リスト＝同種のものの並び / タプル＝異種を束ねた1つのレコード |

面接で 15 秒で答えるなら：「**リストはミュータブル、タプルはイミュータブル。だからタプルは dict のキーになれて、ハッシュ可能。設計の意図としてはリストは同種のコレクション、タプルは異種の値を束ねた『レコード』として使うのが Pythonic**」。

---

## 本質の理解

### なぜ Python に「2つ」必要だったのか

> 「リストの読み取り専用版」だと思っていると面接で詰む。

Guido van Rossum の意図としては:

- **リスト**: 同じ種類のものを並べる（生徒の名前 100 人、ユーザー ID の配列）
- **タプル**: **異なる種類**の値を束ねて 1 つの意味を作る（C 言語の struct みたいに）
  - 例: `(x, y)` の座標、`(name, age, email)` のレコード

「リスト = リスト構造」「タプル = ヘテロな構造体」というイメージ。なので、もしあなたが「3 要素の固定された情報の塊」を扱うなら **タプル** の方が意図が伝わる。

### イミュータブルがもたらす嬉しさ

1. **ハッシュ可能** → dict のキーや set の要素にできる
   ```python
   {(1, 2): "原点近く"}  # OK
   {[1, 2]: "原点近く"}  # TypeError: unhashable type: 'list'
   ```
2. **意図しない変更を防げる**（関数に渡しても破壊されない）
3. **メモリ効率がよい**（拡張のための余分なバッファが不要）
4. **生成が速い**（タプルリテラルはコンパイル時に定数化される）

## 対比表

| 観点 | リスト | タプル |
|---|---|---|
| 記法 | `[1, 2, 3]` | `(1, 2, 3)` |
| ミュータブル | ✅ | ❌ |
| ハッシュ可能 | ❌ | ✅（中身が全てハッシュ可能なら） |
| dict のキーになれる | ❌ | ✅ |
| set の要素になれる | ❌ | ✅ |
| メモリ使用量 | 多め（余剰バッファあり） | 少なめ |
| 生成速度 | 遅い | 速い |
| メソッド | `append, pop, insert, remove, sort, reverse, ...` | `count, index` のみ |
| 想定ユースケース | 同種の要素の集まり | 異種の値を束ねた 1 レコード |
| アンパック | `a, b, c = [1,2,3]` ✅ | `a, b, c = (1,2,3)` ✅ |

## ハンズオン

### 0. REPL を開く

```bash
python3
```

### 1. ミュータビリティを実感する

```python
>>> l = [1, 2, 3]
>>> l[0] = 99
>>> l
[99, 2, 3]

>>> t = (1, 2, 3)
>>> t[0] = 99
Traceback (most recent call last):
  ...
TypeError: 'tuple' object does not support item assignment
```

### 2. `id()` で同一性を見る

```python
>>> l = [1, 2, 3]
>>> id(l)
4378534400
>>> l.append(4)
>>> id(l)
4378534400        # 同じ → 同じオブジェクトの中身が変わった

>>> t = (1, 2, 3)
>>> id(t)
4378529760
>>> t = t + (4,)  # 「追加」ではなく「新しいタプルを作って差し替え」
>>> id(t)
4378612192        # 違う → 別オブジェクト
```

これがイミュータブルの本質。タプルは「変更」できないので、「変えたければ別のものを作る」しかない。

### 3. dict のキーに使う

```python
>>> cache = {}
>>> cache[(3, 4)] = "原点から5"      # タプルはキーOK
>>> cache[(3, 4)]
'原点から5'

>>> cache[[3, 4]] = "..."             # リストはキー不可
TypeError: unhashable type: 'list'
```

座標やキー組合せのキャッシュには**タプル一択**。

### 4. メモリと速度を比較する

```python
>>> import sys
>>> sys.getsizeof([1, 2, 3, 4, 5])
104
>>> sys.getsizeof((1, 2, 3, 4, 5))
80          # タプルの方が小さい

>>> import timeit
>>> timeit.timeit("[1, 2, 3, 4, 5]", number=10_000_000)
0.45
>>> timeit.timeit("(1, 2, 3, 4, 5)", number=10_000_000)
0.10        # タプルの方が圧倒的に速い
```

タプルリテラルは**コンパイル時に定数として確定**するので、毎回オブジェクトを作るリストより速い（dis モジュールでバイトコード見ると差が分かる）。

### 5. アンパックの基本

```python
>>> point = (3, 4)
>>> x, y = point
>>> x, y
(3, 4)

>>> *head, tail = [1, 2, 3, 4]
>>> head, tail
([1, 2, 3], 4)
```

タプルなしには「関数が複数値を返す」が綺麗に書けない:

```python
>>> def divmod_(a, b):
...     return a // b, a % b   # 実はタプルを返している
>>> q, r = divmod_(10, 3)
```

### 6. **罠**: イミュータブルでも中身が変わるケース

```python
>>> t = ([1, 2], [3, 4])
>>> t[0].append(99)
>>> t
([1, 2, 99], [3, 4])
```

「タプル自体は変えていない」（要素 0 が指している先のリストは同じオブジェクト）。**タプルが保証するのは「要素の差し替え不可」であって、要素の中身までは保証しない**。

このため、こういうタプルは**ハッシュ不可になる**:
```python
>>> hash(([1], [2]))
TypeError: unhashable type: 'list'
```

## よくある誤解と落とし穴

### ❌ 「タプルはリストの読み取り専用版」
✅ **設計意図が違う**。
- リスト = 同種の要素の並び（同じ型の集まり）
- タプル = 異種の値を束ねた 1 つのレコード（C の struct 的）

この意図に従えば、関数が複数値を返すのは「リストではなくタプル」だと自然に書けるようになる。

### ❌ 「`(1)` が要素 1 つのタプル」
✅ `(1)` は **ただの整数** に括弧をつけたもの。要素 1 つのタプルは **`(1,)` （末尾カンマ）**。

```python
>>> type((1))
<class 'int'>
>>> type((1,))
<class 'tuple'>
>>> type(())          # 空タプルは括弧だけでOK
<class 'tuple'>
```

### ❌ 「タプルだから中身も変わらない」
✅ **タプル「自体」は変わらないが、要素が指している先がミュータブルならそこは変わる**。上のハンズオン 6 を参照。

「ハッシュ可能 = 完全にイミュータブル」ではなく「**直接含むものがハッシュ可能なら自分もハッシュ可能**」。

### ❌ 「リスト内包表記とジェネレータ式は記法だけの違い」
✅ 違う。
- リスト内包 `[x for x in ...]` → 全部を**メモリに展開**
- ジェネレータ式 `(x for x in ...)` → **遅延評価**（1 個ずつ生成）

`(x for x in ...)` は**タプルではなくジェネレータ**になる点に注意（タプルにしたければ `tuple(x for x in ...)`）。

### ❌ 「データを返すならいつもタプルでよい」
✅ フィールド数が 3 を超えるなら **`namedtuple`** か **`dataclass`** の方が読みやすい:

```python
# つらい
def get_user(): return ("taro", 30, "taro@example.com", True)
name, age, email, active = get_user()  # 順序を覚える必要あり

# 読みやすい
from dataclasses import dataclass
@dataclass(frozen=True)  # frozen=True で immutable
class User:
    name: str
    age: int
    email: str
    active: bool
```

## 章末 Q&A

**Q1. なぜタプルは dict のキーに使えるのか？ 一言で。**

<details>
<summary>解答</summary>

**イミュータブルだからハッシュ値が変わらない**から。dict はキーのハッシュ値で内部の格納場所を決めるため、後からハッシュ値が変わるとキーを引けなくなってしまう。リストはミュータブル → ハッシュ値が変わりうる → だから `unhashable` として弾かれる。
</details>

**Q2. `(1)` と `(1,)` の違いは？**

<details>
<summary>解答</summary>

- `(1)` → ただの整数 1（括弧は式のグルーピング）
- `(1,)` → **要素が 1 つのタプル**

タプルを作る本質は「カンマ」であって括弧ではない。実は `1, 2, 3` だけでもタプルになる（括弧はあくまで可読性のため）。
</details>

**Q3. `t = ([1, 2],); t[0].append(3)` がエラーにならないのはなぜ？**

<details>
<summary>解答</summary>

タプルが保証するのは「**自分が指している参照の差し替え不可**」。`t[0]` が指しているリストオブジェクトは**同じまま**で、リストオブジェクトの中身が変わっているだけだから、タプルとしての契約は破られていない。

`t[0] = [...]` のように差し替えようとすると TypeError になる。
</details>

**Q4. 関数で複数の値を返したい時、リストとタプルどちらを使うべき？**

<details>
<summary>解答</summary>

**タプル**。Python 的にも `return a, b` と書けば自動でタプルになる。理由：
- 返ってくる値は「**意味の異なる複数の値の束**」であって、同種の集合ではない
- 受け取り側が `q, r = func()` のようにアンパックする使い方と相性がいい
- イミュータブルなので破壊される心配がない

ただしフィールド数が増えるなら `namedtuple` か `dataclass` を使うべき（位置で覚えないと読めなくなる）。
</details>

**Q5. リスト内包表記 `[x*2 for x in big_list]` とジェネレータ式 `(x*2 for x in big_list)` の使い分け？**

<details>
<summary>解答</summary>

- **リスト内包**: 結果を**全部メモリに展開**する。後で何度も使う、ランダムアクセスする、`len()` 取りたい場合に良い
- **ジェネレータ式**: 結果を**遅延評価**して 1 個ずつ生成。巨大なデータを 1 度だけ走査する場合にメモリ効率が圧倒的に良い

例: 10 億行のログを処理するなら `sum(int(x) for x in lines)` のように**ジェネレータ式 + sum/any/max** などで「1 個ずつ消費しながら集約」する。リスト内包で全展開するとメモリが死ぬ。

なお `(x for x in ...)` の結果は**タプルではなくジェネレータ**であることに注意。
</details>
